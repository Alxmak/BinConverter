## Четыре правила переноса

Скрипт написан под однопоточную консольную среду с одним глобальным буфером. Прямой перевод даст нетестируемый код, поэтому четыре решения фиксируем до начала работы — дальше весь план на них опирается.

### 1. Core молчит

В скрипте детектор сам печатает в лог и сам открывает диалоги (`DIALOG.getInt32` при неопознанной геометрии NAND, `messageBox` при переименовании дампа Philips). В `TweakFirmware.Core` так нельзя — там уже принято возвращать `Status`-перечисление и объект-результат, а решения о показе принимает ViewModel. Всё то же самое: детектор *возвращает* находки и *запрашивает* недостающее через интерфейс-колбэк.

```
public interface IAnalysisHost
{
    void Log(string message, LogLevel level = LogLevel.Info);
    Task<int?>  AskNandGeometryAsync(IReadOnlyList<NandGeometry> options, CancellationToken ct);
    Task<bool>  ConfirmAsync(string question, CancellationToken ct);
    IProgress<long>? Progress { get; }
}
```

В тестах подставляется `FakeAnalysisHost`, который отвечает заранее заданными значениями и копит журнал в список.

### 2. Явный буфер вместо глобального BUFFER

Это главная ловушка. Половина детекторов передаёт данные между методами *через* общий буфер: `mediatek_nand.check()` оставляет в нём страницу, а `read_parts()` её читает; `lg_nand.check_signature()` ещё и переворачивает там байты перед разбором. Такая связь невидима в сигнатурах и при переносе рвётся молча.

Поэтому детектор получает форму из двух шагов, где найденное передаётся явно:

```
public interface ILayoutDetector
{
    string Name { get; }
    LayoutDetection? TryDetect(IDumpReader dump, DumpContext ctx, IAnalysisHost host, CancellationToken ct);
    void ReadParts(LayoutDetection detection, PartitionTable table, DumpContext ctx, IAnalysisHost host);
}

public sealed record LayoutDetection(string MarkName, long TableOffset, byte[] Table);
```

Список детекторов, где это обязательно (буфер переживает вызов): MEDIATEK_NAND, MSTAR_NAND, MTK_LG, LG_NAND, ROCKCHIP_PX3, MPT_AMLOGIC, GPT, MTK_ANDROID, HISILICON, NVT_NAND, RECEIVER_ANDROID, NORFLASH.

### 3. Логические координаты внутри, физические — на границе

Как в оригинале: `PartitionEntry.Offset/Length` всегда «без spare». Конвертация — только в трёх точках: печать таблицы, запись второго `.udev`, извлечение файлов. В отличие от скрипта, где это делают функции с побочным эффектом на весь массив, в порте пусть будет чистая функция `NandGeometry.ToPhysical(entry)`, возвращающая копию.

### 4. Порядок детекторов — данные

Цепочка из `else if` превращается в упорядоченный список с приоритетами. Порядок обязан совпасть с оригиналом до последнего элемента: он подобран так, что узкие признаки идут раньше широких, и любая перестановка меняет результат на реальных дампах.

> **Внимание.** **Не «улучшать» здесь ничего.** В частности, NAND-цепочка в оригинале — *отдельный* блок `if`, а не продолжение общей. Значит, для NAND-дампа с найденной MBR NAND-детекторы всё равно отработают и допишут разделы. Это выглядит как недосмотр, но на дампах телевизоров даёт рабочий результат — переносим как есть, через два независимых прохода `RunChain(commonChain)` и `if (geometry != null) RunChain(nandChain)`.

## Ключ к переводу кода: семантика BUFFER

Без этого абзаца перенос сломается в сотне мест, и сломается тихо — числами, похожими на правду.

> **Важно.** **`BUFFER.read16/32/64(value, pos)` принимает не байтовое смещение, а *индекс элемента*.** То есть `read32(x, 3)` читает байты `0x0C…0x0F`, а `read64(x, 0x200/8)` — восемь байт по адресу `0x200`. Порядок байт — little-endian. Официальная формулировка: «Reads the dword to value at index position pos in the BUFFER».

Отсюда два следствия, которые надо держать в голове при каждой строке:

- **Каждый вызов конвертируется умножением.** `read32(v, N)` → байтовое смещение `N * 4`. В скрипте это уже видно по идиоме `read32(x, addr/4)` — там, где автор писал адрес явно, он делил его на размер типа.
- **Индексация не даёт прочитать невыровненное значение** — именно поэтому в скрипте есть `read16/32/64FromBufferLittleEndian()`. Они нужны не для смены порядка байт (он и так LE), а чтобы прочитать поле по нечётному адресу: `0x0B` (байт/сектор в BPB), `0x11`, `0x13`, `0x24`, `0x2C`, `0x32`.

В C# оба случая схлопываются в один вызов, и вспомогательные функции не нужны:

| AngelScript | C# |
| --- | --- |
| BUFFER.read8(v, n) | buf[n] |
| BUFFER.read16(v, n) | BinaryPrimitives.ReadUInt16LittleEndian(buf.AsSpan(n * 2)) |
| BUFFER.read32(v, n) | BinaryPrimitives.ReadUInt32LittleEndian(buf.AsSpan(n * 4)) |
| BUFFER.read64(v, n) | BinaryPrimitives.ReadUInt64LittleEndian(buf.AsSpan(n * 8)) |
| read32FromBufferLittleEndian(off) | BinaryPrimitives.ReadUInt32LittleEndian(buf.AsSpan(off)) |
| reverseBytes32(x) | BinaryPrimitives.ReverseEndianness(x) |
| BUFFER.readString(s, off, len) | Encoding.ASCII.GetString(...) до первого 0x00 |
| BUFFER.findString(s, pos, size) | IndexOf по span; тип результата **int**, не uint |

> Сигнатуры-константы вида `0x5452415020494645` («EFI PART») и `0xE7F435B9F9BC3947` (Novatek, в дампе лежит как `47 39 BC F9 B9 35 F4 E7`) переносятся *без изменений* — они уже записаны как little-endian значения.

**Приёмочная проверка этапа:** написать тест, который для каждого детектора подаёт синтетическую таблицу и убеждается, что прочитаны те же поля, что в оригинале. Расхождение в множителе даёт смещение ровно в 4 или 8 раз — заметно сразу.

## Формат .udev — дословно

В скрипте формат не виден: его пишет сам программатор через `PARTITIONS.saveToUDEV()`. Чтобы файлы из BinConverter открывались в UFPI, воспроизводим формат точно. Он INI-подобный, кодировка UTF-8.

#### eMMC

```
[DESC]
Name = Partitions
FlashType1 = eMMC
FlashBase1 = 0

[PARTITIONS]
PartitionsMode = true
;Начальный адрес, Размер, Имя, Часть(USER/BOOT1/BOOT2/RPMB), Имя файла, Смещение в файле, ФС
0x0000000000,0x00200000,Partitions_table,USER,
0x00030C0000,0x2BC00000,system,USER,USER_0x00030C0000_0x2BC00000_system.bin,0,EXT4
0x002ECC0000,0x40400000,userdata,USER,,,EXT4
```

#### NAND

```
[PARTITIONS]
PartitionsMode = true
; если адреса разделов указаны с учётом spare
RawAddrMode = true
; если размеры разделов указаны без учёта spare
RawSizeMode = false
0x00000000,0x1950000,UBOOT
0x01950000,0x1734000,UBOOTENV
```

| Поле | Значения | Откуда в порте |
| --- | --- | --- |
| Адрес, Размер | 0x… , 10–12 разрядов | `PartitionEntry.Offset/Length` |
| Имя | строка без запятых | `Name`, после `checkPartsNames` |
| Часть | USER / BOOT1 / BOOT2 / RPMB | всегда `USER` — скрипт другого не создаёт |
| Имя файла | USER_0x…_0x…_имя.bin | то же имя, что при извлечении |
| ФС | EXT4 / FAT16 / FAT32 / NTFS / SQUASHFS | `FsType`; прочие типы пишутся пустым полем |

> Схема имён `USER_0x<адрес>_0x<размер>_<имя>.bin` из `extract_part()` — не самодеятельность автора, а «соглашение» UFPI: по таким именам программатор умеет обратно наполнять таблицу разделов кнопкой «Загрузить из папки». Менять шаблон нельзя, иначе сломается связка с программатором.

Флаги `RawAddrMode` / `RawSizeMode` соответствуют битам `PARTS_FLAG_RAW_ADDR` / `PARTS_FLAG_RAW_SIZE`. Скрипт их не выставляет — вместо этого пишет два файла (в логических и в физических координатах). В порте оставляем то же поведение, но флаги проставляем явно: это ровно та информация, которой в оригинальных файлах не хватает.

## Чтение дампа и геометрия NAND

Самый ответственный этап: на нём стоит всё остальное. Делать до детекторов, тестировать особенно плотно.

### 1.1 IDumpReader

Абстракция поверх файла. Единственный метод чтения принимает *логическое* смещение — как `loadData()`.

```
public interface IDumpReader : IDisposable
{
    long PhysicalSize { get; }   // FILE.size()
    long LogicalSize  { get; }   // fileSizeMinusSpare
    int  Read(long logicalOffset, Span<byte> destination);
    byte[] ReadBlock(long logicalOffset, int length);
}
```

`PlainDumpReader` — тривиальная реализация для eMMC.

### 1.2 NandGeometry

Неизменяемая запись: `Main`, `Spare`, `Page = Main + Spare`, `RelativeMain`, `RelativeSpare`, `Layout` (`None` / `Standard` / `DuneHd`). Плюс два метода-переводчика, дословно из скрипта:

```
public long AddSpare  (long x) => x / Main * Page  + x % Main;
public long MinusSpare(long x) => x / Page * Main  + x % Page;
```

Тест: для любого `x`, кратного `Main`, композиция обеих функций даёт исходное значение.

### 1.3 NandGeometryDetector — два шага

**Шаг 1, соотношение по размеру файла.** Порог 64 МиБ, затем сдвиг вправо до первой единицы и таблица соответствий `0x11`→(16,1), `0x21`→(32,1), `0x45`→(64,5), `0x87`→(128,7), `0x10F`→(256,15), плюс частный случай `0x88A7D800`→(0x800,0x6D) для K9GAG08U0E.

**Шаг 2, размер страницы по статистике `0xFF`.** Переносится буквально, включая эмпирические пороги: кандидат — блок, где `max_spare/16 < count₀ₓFF ≤ max_spare`; из семи гипотез `main` побеждает та, где в предполагаемых зонах spare больше всего `0xFF`; вариант 16384 отбраковывается; результат принимается при `max ≥ max_spare/8`.

> **Внимание.** Пороги `/16`, `/8` и отбраковка индекса 6 выглядят произвольно, но они подобраны автором по реальным дампам. Не трогать и вынести в `const` с комментарием, откуда взялись.

Не сошлось — `host.AskNandGeometryAsync()` с теми же девятью вариантами (main 256…32768 и «нет spare»).

### 1.4 NandDumpReader — пять режимов loadData

Все пять веток оригинала, в том же порядке проверки:

1. **Blueray нестандартный** — субстраницы `main + spare` и хвост `block_0xFF`. Условие включения: разметка опознана как Blueray и при этом `main ≠ 0x400` или `spare ≠ 0x20`.
2. **Dune HD** — жёсткая раскладка страницы `0x840`: 4 байта метки, 512 данных, 13 spare, ещё дважды 512+13, 469 данных, 6 байт мусора, 43 данных, 13 spare, 2 байта мусора.
3. **Кэш** — окно 2 МиБ, промах при трёх условиях оригинала. Для NAND сырой блок читается кратно страницам, затем main уплотняется на месте.
4. **Standard без кэша** — постранично.
5. **eMMC** — прямое чтение.

> Первая ветка зависит от уже определённой разметки — то есть от результата детектора, который сам пользуется этим ридером. В порте это решается флагом `BluerayPageLayout?`, который выставляет детектор Blueray после успеха, а ридер учитывает при последующих чтениях. Порядок вызовов оригинала при этом сохраняется.

> **Готово, когда:** тест собирает NAND-образ `DumpBuilder`-ом, читает случайные логические диапазоны и сверяет их с исходным логическим массивом — байт в байт, включая чтения, пересекающие границы страниц и границу кэша.

## Модель разделов и нормализация

### 2.1 PartitionEntry

```
public sealed class PartitionEntry
{
    public string  Name    { get; set; } = "";
    public long    Offset  { get; set; }
    public long    Length  { get; set; }      // знаковое: <0 = «до конца дампа»
    public FsType  FsType  { get; set; }
    public string  Comment { get; set; } = "";
    public byte    MbrType { get; set; }
    public byte    MbrStatus { get; set; }
    public int     BadBlocks { get; set; }
    public bool    Selected { get; set; } = true;   // галочка в таблице
}
```

> **Внимание.** `Length` обязан остаться знаковым. Значение `-1` приходит из записей `-(userdata)` и `-@0x00204000(userdata)` и разворачивается в настоящий размер только на шаге `AddGaps`. Беззнаковый тип здесь ломает последний раздел на большинстве дампов Android.

### 2.2 PartitionTableNormalizer — шесть шагов

Ровно та последовательность, что в оригинале, каждый шаг — отдельный публичный метод (так их можно тестировать поштучно):

| Метод | Оригинал | Что делает |
| --- | --- | --- |
| FixNames | checkPartsNames | Обрезает имя на первом символе < `0x20` |
| SortByOffset | sorting_parts | Устойчивая сортировка по возрастанию смещения |
| AddGaps | add_gaps | Разворачивает отрицательные длины, вставляет `gap_NN` |
| RemoveDuplicates | deletingPartsDuplicates | Убирает соседние записи с одинаковыми offset+len+name |
| MarkEmpty | checkListEmpty | Комментарий «empty» для разделов из одних `0x00`/`0xFF` |
| AttachBadBlocks | add_bb_to_part_table | Считает бэд-блоки, попавшие в раздел |

Порядок вызова в оркестраторе — `FixNames → Sort → AddGaps → Sort → RemoveDuplicates`. Двойная сортировка не избыточна: `AddGaps` дописывает записи в конец.

#### AddGaps: две разные задачи в одной функции

Первая — если у последнего раздела длина отрицательна, она равна `LogicalSize − Offset`. Особый случай: смещение последнего раздела больше размера файла (строка mtdparts описывает микросхему большего объёма, чем имеющийся дамп) — тогда размер дампа домысливается как ближайшая сверху степень двойки от этого смещения. Второй — обычная вставка промежутков, включая хвост до конца дампа.

> **Готово, когда:** есть тест на каждый из шести шагов и отдельный — на связку из строки `...,-(NA)` с проверкой, что последний раздел дотянулся ровно до конца.

## Парсер строк mtdparts

Делать третьим, до всех детекторов: восемь разметок сводятся именно к нему, а тестировать его можно вообще без дампа.

### 3.1 MtdPartsParser

Алгоритм оригинала без изменений: отбросить всё до первого двоеточия; резать по запятым; прерваться, если встретился пробел или `%`; из каждой подстроки взять имя из скобок, комментарий — после закрывающей скобки, смещение — после `@`, длину — из остатка; при отсутствии `@` накапливать смещение самому.

Тестовый набор берём прямо из комментариев скрипта — там три реальные строки:

```
2560k@0x380000(MBOOT),2560k(MBOOTBAK),4m(UBILD),10m(KL),40m(CONF),199m(UBIA),9m(tee),-(NA)

0x00002000@0x00002000(uboot),0x00006000@0x00006000(kernel),-@0x00204000(userdata)

mtdparts=mt53xx-emmc:2M(uboot),2M(uboot_env),256k(part_02),8M(perm),2048M(data)
```

Плюс случай с суффиксом-комментарием: `8M(perm)enc`.

### 3.2 SizeToken — разбор числа с множителем

Поддерживаем всё, что понимал оригинал: `-` → «до конца», `0x…`/`0X…` → шестнадцатеричное, десятичное с `k`/`K` (×1024) и `m`/`M` (×1024²).

> **Исправление 1.** Добавляем `g`/`G` (×1024³) и голое десятичное без суффикса (множитель 1). Оригинал на них печатал «Error when decoding multiplier» и возвращал `-1`, то есть эти входы и так не работали — расширение ничего сломать не может.

### 3.3 Сценарий «файл — это строка разделов»

Аналог `checkTableInString()`: файл меньше 10 000 байт трактуется как текст со списком разделов. После разбора — вопрос через `host`, надо ли пересчитать размеры под NAND, и запрос `main`/`spare`. Сохраняем как есть, включая порог 10 000.

## Детекторы eMMC — общая цепочка

Одиннадцать детекторов в порядке оригинала. Каждый — отдельный класс с `Priority`, соответствующим позиции в цепочке.

### 4.1 MBR / EBR / GPT — начинать отсюда

Самый объёмный и самый переиспользуемый детектор.

- **MBR:** `0xAA55` в секторе 0 *и* проверка, что это не FAT-загрузчик (`fat.checkType(offset) == fsUNKNOWN`) — иначе том FAT будет принят за MBR. Записи по 16 байт с `0x1BE`.
- **EBR:** рекурсивная цепочка. Первая запись — раздел относительно текущего сектора EBR, вторая — следующий EBR относительно *начала* расширенного раздела. Ограничение глубины на всякий случай (в оригинале рекурсия без предохранителя).
- **GPT:** «EFI PART», CRC32 заголовка с обнулённым полем CRC, CRC32 таблицы, разбор записей (first LBA @`+0x20`, last LBA @`+0x28`, имя UTF-16 из 36 символов @`+0x38`, непечатаемые отбрасываются). Отдельными разделами добавляются `GPT_header` и `GPT_table`, затем проверяется резервная копия.

> **Внимание.** GPT в оригинале вызывается из двух мест с чуть разной логикой: из `analysisDump` напрямую по типу `0xEE` и из `mbr.addParts()`. Фактически работает первый путь. В порте достаточно одного, но поведение (порядок добавления `GPT_header`, `GPT_table`, разделов, затем проверка резервной) сохранить дословно.

### 4.2 Табличные: China Android, MPT Amlogic, MTK_LG

Простые бинарные таблицы, переносятся механически. Смещения полей — из сводной таблицы разбора (раздел 7 справочника). Внимание к двум местам:

- **China Android** при `i == 0` дополнительно добавляет искусственный раздел `Partitions_table` от нуля до начала первого раздела.
- **MTK_LG** имеет два формата записи, выбираемых по значению сигнатуры-даты: `0x20110620` и `0x20110609` → запись `0x58` с 32-битными полями, `0x20120716` → запись `0x60` с 64-битными.

### 4.3 Строковые: MTK Android, Rockchip PX3, Receiver Android, NOR flash

Все четыре — «найти блок, проверить CRC32, вытащить строку, отдать парсеру этапа 03».

Общий помощник `Crc32BlockProbe(dump, offset, blockLength)`: читает блок, берёт `uint32` из первых четырёх байт и сверяет с CRC32 остатка. Используется MTK Android (`0x20000`), Receiver Android (`0x10000`), NOR (`0x10000`), HiSilicon (4096) и MSTAR NAND (четыре варианта длины).

Rockchip дополнительно требует `correctSizesForEmmc()` — все размеры в его строке в секторах, умножаются на 512.

### 4.4 Sony MediaTek eMMC — три стратегии

Самая новая часть скрипта, переносить целиком и в правильном порядке: сначала `CheckGN5UR`, затем `CheckSkanDumpMap`, затем `CheckFloatingMap`.

- Первые две — фиксированные карты (40 и 37 разделов) плюс диапазон размера дампа и 8–10 контрольных точек.
- Третья ищет те же якоря функцией `FindSigNear(центр, радиус, тип)` с шагом 1 МиБ и требует, чтобы все десять нашлись *и* шли строго по возрастанию.
- Размер `data` в плавающем режиме считается из суперблока: `Ext4SizeAt()` читает `blocks_count_lo` (`+0x404`) и `log_block_size` (`+0x418`), при `log > 8` откатывается на «до конца дампа».

Три микро-проверки сигнатур (`CheckExt4`, `CheckFat16`, `CheckAvb`) выносим в общий класс — они пригодятся и зондам ФС этапа 06.

Фиксированные карты — это данные, а не код: держим их в двух статических массивах `(name, offset, length, fs)`, чтобы новые модели добавлялись строкой.

> **Готово, когда:** для каждого детектора есть тест «синтетический дамп с сигнатурой → ожидаемый список разделов» и тест «дамп без сигнатуры → детектор молчит».

## Детекторы NAND — вторая цепочка

Двенадцать детекторов, выполняются отдельным проходом при `geometry != null`. Все читают через `NandDumpReader`, то есть в логических координатах.

### 5.1 Простые табличные: Ambarella, Novatek, SAT Receiver, Blueray

Ambarella — два формата записи (`0x10` и `0x28`), конец таблицы по маркеру `0x33219FBD`, смещения и размеры в блоках по `0x20000`.

SAT Receiver — единственный, где поля big-endian (`reverseBytes32`), а адреса пересчитываются как `addSpare(x) + x % nandMain`.

Blueray — кроме таблицы определяет геометрию страницы: ищет прогон из `0xFF`, чтобы вычислить `block_0xFF` и `numberSubpagesInPage`. Результат нужен ридеру этапа 1.4, поэтому детектор возвращает его в `DumpContext`.

### 5.2 Строковые NAND: NVT, HiSilicon, Mediatek, MSTAR

MSTAR NAND — самый дорогой по времени: перебор `0x200000`…`0x4000000` с шагом `0x1000`, на каждом шаге эвристика «больше трёх знаков `=` в байтах 4…`0x7F`», и только затем CRC32 в четырёх вариантах длины. Обязательно с отчётом прогресса и поддержкой отмены.

> **Исправление 2.** В `MEDIATEK_NAND.read_parts()` результат `findString` присваивается в `uint`, после чего проверка `if (index < 0) return;` не срабатывает никогда, и при отсутствии строки разбирается мусор. В C# тип результата — `int`, проверка работает. Ошибка очевидная и односторонняя: чинит только случай промаха.

### 5.3 LG NAND + таблица бэд-блоков

Четыре карты (`mstar_map0`, `bcm35230_map0`, `3mcb_xx50pam`, `douglas_map0`), у двух из них — свои особенности: для `3mcb_xx50pam` вся таблица переворачивается по 4 байта, для `douglas_map0` буфер сдвигается на 4 байта вправо, а поля offset/len дополнительно меняют порядок байт.

`bbminfo_analysis()`: сигнатура `0xA6A59281` (в обоих порядках), пары `remaped_to/remaped_from`, число блоков в дампе выводится округлением первого `remaped_to` вверх до степени двойки.

### 5.4 Samsung NAND, Dune HD, Philips QFU

**Samsung** — сканирование *с конца* дампа постранично в поисках `LPCH` и `UPCH`; размер блока = модуль их разности; таблица `FSRPART`; затем BBT из пар `uint16` до `0xFFFF`.

**Dune HD** — текстовый конфиг с ключами `product_id`, `board_id`, `_parts`, `_partN_offset/_size/_name`. Плюс побочная функция: поиск и извлечение файла лицензии `./dune_license.dlf` (сканирование блоками по 64 страницы с шагом `0x200`, содержимое — со смещения `+0x200` до нулевого байта). Её тоже переносим — это часть заявленной функциональности.

**Philips QFU** — см. этап 09, там же его побочные действия с файлом.

> **Готово, когда:** все 12 детекторов имеют тесты, а прогон полной цепочки по синтетическому NAND-дампу даёт тот же список, что и по эквивалентному логическому образу.

## Зонды файловых систем

### 6.1 Восемь зондов

```
public interface IFileSystemProbe
{
    FsType Type { get; }
    VolumeInfo? TryProbe(IDumpReader dump, long offset, long partitionEnd);
}
```

Порядок опроса — как в `scanFS`, менять нельзя: **ext4 → SquashFS → ROMFS → FAT → VDFS → CRAMFS → TAR**.

Детали, которые легко потерять:

- **ext4** дополнительно требует, чтобы первые `0x400` байт были заполнены нулями или `0xFF`, и чтобы `block_size == fragment_size` и `< 7`. Имя тома берётся из метки, при её отсутствии — из last-mounted path, иначе `"part"`.
- **SquashFS** — четыре версии и оба порядка байт; поля читаются по-разному для каждой версии. Проверка `block_log` против `block_size` даёт предупреждение о повреждении, но том всё равно добавляется.
- **FAT** — полная валидация BPB перед решением; тип по числу кластеров (<65525 → FAT16), затем уточнение по меткам `"FAT16 "`/`"FAT32 "`. Сравнение копий FAT и подсчёт свободных кластеров сохраняем — это то, что выводится в журнал.
- **VDFS** — две раскладки: layout version `"0001"` и все прочие; плюс отдельная ветка для `"1eMMCFS"`.
- **TAR** — проверка и unsigned-, и signed-суммы заголовка, шаг по блокам 512 до первого невалидного.

Если том вылезает за границу раздела, размер обрезается по границе, а в комментарий пишется предупреждение — так в оригинале для ext4 и FAT.

### 6.2 FileSystemScanner

Аналог `scanFS`. Нашли том — прыгаем на его размер, выровненный вверх до 512; не нашли — на один шаг.

> **Исправление 3.** В оригинале шаг сканирования вычисляется из глобальных `addr` и `volumeSize`, оставшихся от *предыдущего* вызова функции. Намерение видно из кода: шаг `0x1000` при выровненном адресе, иначе 512. В порте считаем от переданного `offset` раздела. На практике оригинал почти всегда получал `0x1000`, так что поведение не меняется, но перестаёт зависеть от истории вызовов.

Замена раздела найденными томами — как в оригинале: если внутри раздела что-то нашлось, исходная запись удаляется, а первому тому без собственного имени присваивается имя раздела. Разделы с именами, начинающимися на `MBR` и `EBR`, не сканируются.

## Обход ext4 и разбор build.prop

### 7.1 Ext4DirectoryReader

Минимальный обход: суперблок → дескрипторы групп (следующий блок после суперблока, номер блока таблицы инод по `+0x08` каждого 32-байтового дескриптора) → таблицы инод → записи каталога (inode `u32`, длина записи `u16` @`+4`, длина имени `u8` @`+6`, тип `u8` @`+7`, имя @`+8`).

Инода: магия `0xF30A` по `+0x28`, размер из `+0x04` и `+0x6C`, номер первого блока из `+0x3C`.

> **Внимание.** Это чтение «только первого экстента»: файл считается непрерывным. Для `build.prop` достаточно, для произвольных файлов — нет. Переносим как есть и пишем это в XML-комментарии, чтобы через полгода не принять за полноценный ext4-ридер.

В оригинале таблицы инод грузятся в общий буфер по фиксированному смещению `0x100000` с `BUFFER.resize(20 МБ)`. В порте — собственный массив внутри класса, размер считается от `inodeSize × inodesPerGroup × числа групп`.

### 7.2 AndroidInfoReader

Сначала ищется ext4-раздел с именем `system`, иначе перебираются все ext4. В корне тома ищется `build.prop`; не найден — спуск в каталог `system`.

Разбор: сперва `ro.build.fingerprint=` по разделителям `/` и `:` (brand / name / device / release), иначе каждое поле отдельно. Дополнительно `.manufacturer`, `.platform`, `.board`, `.model`, `.swversion`, `.hwboard`, `.display-size`.

Файл сохраняется рядом с дампом как `BuildProp.txt` — имя оставляем прежним для совместимости с привычками пользователей.

## Вывод: .udev, извлечение, разрезание

### 9.1 UdevWriter

Пишет формат из раздела «Формат .udev» — UTF-8, секции `[DESC]` и `[PARTITIONS]`. Для NAND выставляет `RawAddrMode` / `RawSizeMode` в соответствии с тем, в каких координатах записан конкретный файл.

Тест: сгенерированный файл разбирается собственным же читателем и даёт исходную таблицу; плюс проверка на дословное совпадение с образцом из руководства.

### 9.2 PartitionExtractOperation

Извлекает отмеченные разделы. Имя файла — строго по соглашению UFPI, с расширением ФС перед `.bin`. Для NAND пишутся два файла: полный и очищенный от spare (в папку `_onlyMain_`), для нестандартного Blueray — по его субстраничной раскладке.

> **Исправление 5.** Папка назначения в оригинале выбирается по глобальному флагу `marksOff_PartitionsOn`, который к моменту нажатия «Erase» хранит результат прошлого анализа. Из-за инверсии в условии результат поиска *файловых систем* попадает в папку `_parts_`, а результат поиска *разметки* — в `_fs_`. В порте суффикс приходит явным параметром `ExtractionSource.PartitionTable → "_parts_"` / `FileSystems → "_fs_"`. Оба имени папок сохранены, а зависимость от устаревшего глобального состояния исчезает.

> **Исправление 6.** Оригинал перебирает индексы по `PARTITIONS.count()`, а данные берёт из `part[i]` — два списка совпадают только по договорённости. В порте список один, поэтому проблема снимается конструкцией.

Переиспользуем то, что уже есть в проекте: `PauseController` (пауза/возобновление), `FileConflictHelper` и `OutputCollision` (конфликты имён), `IncompleteOutput` (удаление недописанных файлов при отмене), `DiskSpaceHelper` (проверка места до начала).

### 9.3 NandSplitOperation

Аналог кнопки «Blank Check»: `main.bin` и `spare.bin` рядом с дампом; для Dune HD — только `main.bin`.

> **Исправление 7.** Оригинал накапливает *весь* spare в массиве в ОЗУ, затем копирует его в буфер и только потом пишет. Для дампа 8 ГиБ это сотни мегабайт впустую. В порте — два `FileStream` и потоковая запись обоих файлов за один проход. Результат побайтово идентичен.

### 9.4 Philips QFU: идентификация и переименование

Единственное место, где скрипт меняет исходный файл. Переносим обе ветки — NAND (поиск блока `SW version / Set type / Set serial` в области RWBOOT, удаление дубликатов, предложение переименовать в `<модель> <версия> <серийник>.bin`) и EEPROM 24C64 (метка `FUSIO` по `0x20`, модель, серийник, блок опций, переименование в `<модель> <серийник> 24C64.bin`).

> **Внимание.** Переименование выносим в явную кнопку в интерфейсе, а не в автоматический диалог посреди анализа. Функция сохраняется полностью, но пользователь не получает вопрос о переименовании тогда, когда он его не ждёт.

## Приёмка

### 11.1 Сверка с оригиналом

Главный критерий: на одном и том же дампе BinConverter и скрипт в UFPI должны давать *одинаковый* список разделов — те же имена, смещения, размеры, типы ФС и тот же порядок.

Практический способ: прогнать скрипт в UFPI, сохранить `.udev`, затем прогнать BinConverter и сравнить файлы. Различия должны сводиться к отметке времени в имени.

Набор дампов для сверки стоит собрать заранее — по одному на семейство: MSTAR Android, MTK LG, LG NAND, Samsung NAND, Sony MTK eMMC, Philips QFU, Dune HD, NOR SPI.

### 11.2 Автотесты

- Парсер mtdparts — ≥15 случаев.
- Геометрия NAND — все шесть вариантов соотношения плюс отказ.
- addSpare/minusSpare — свойство обратимости.
- Каждый детектор — «находит» и «не находит».
- Каждый зонд ФС — то же.
- Нормализатор — шесть шагов плюс связка.
- UdevWriter — совпадение с образцом из руководства.

## После аудита

### Девять падающих тестов

В проекте оставались девять тестов, падавших вне Windows. Причина оказалась не в коде: тесты зашивали пути вида `C:\dumps\emmc.bin`, а вне Windows это не путь, а имя файла целиком — обратная косая черта там обычный символ, `Path.GetFullPath` приписывает такую строку к текущей папке, а `Path.GetExtension` не отделяет папку от имени. Проверяемый код верен: под Windows он работает как задумано.

Поэтому правились тесты, а не программа. Помощник `TestPaths` собирает путь по правилам той системы, где идёт прогон, и один и тот же тест проверяет одно и то же поведение везде. Попутно выяснилось, что тест `ChainIncludes_IgnoresCase` раньше проходил **случайно**: обе строки одинаково приписывались к текущей папке и совпадали.

> **520 из 520** на Windows и столько же на Linux. Падающих не осталось.

### Проверка сборки на рабочих ветках

Прогон `build-check.yml` срабатывал только на `main`, поэтому ветка ни разу не собиралась под Windows. В триггер добавлены ветки `claude/**`: сборка идёт на `windows-latest`, а расхождения вроде тех самых путей лучше видеть до слияния.

### Слияние в main

Влито перемоткой — `main` не двигалась с момента ответвления, поэтому ни коммита слияния, ни конфликтов, ни принудительного пуша. Попутно выяснилось, что локальная `main` в рабочем окружении была посторонней историей из трёх коммитов без общего предка с настоящей; её не трогали, пуш шёл напрямую из рабочей ветки.

### Пометка «Beta» у пункта меню

Подпись вкладки получила надстрочную красную приписку. Одной строкой в `Content` часть текста не поднять и не покрасить, поэтому она собрана из двух `Run` — и это потянуло за собой три неочевидных следствия:

- цвет основной подписи привязан к `Foreground` самого пункта меню, а не оставлен на наследование: в этом дереве оно доходит не до всех элементов, о чём в `AppStyles.xaml` уже была записка, и подпись почернела бы на тёмной теме;
- `TargetPageTag` задан явно. По IL `NavigationViewItem.OnInitialized` из WPF-UI 4.3 видно, что при нестроковом `Content` он берёт `Content.ToString()` — тег стал бы именем типа;
- красный взят своим ресурсом, а не кистью темы: подходящий ключ подтвердить не удалось, а несуществующий `DynamicResource` **не красит молча** — приписка осталась бы цветом обычного текста, и на сборке это никак не проявилось бы.

> **Сверка с UFPI.** Этап 11.1 плана — прогнать один дамп через оригинальный скрипт в UFPI и через вкладку, сравнить `.udev` и имена извлечённых файлов побайтно. Это остаётся за вами: программатора и контрольных дампов в окружении нет.
